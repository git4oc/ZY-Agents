## 2. 检测手段分类

| 标记 | 含义 | 在哪执行 |
|---|---|---|
| `CI-AST` | 静态检查：import 图、AST 签名快照、正则黑名单 | CI（PR 必跑） |
| `CI-SCHEMA` | 契约与配置比对：`schema_version`、版本锁、`compat-matrix.yaml` | CI（PR 必跑） |
| `CI-TEST` | 自动化测试断言（含负向用例） | CI（PR 必跑） |
| `NET` | **网络层**验证：抓实际字节流，不经前端 | 集成测试 |
| `RUNTIME` | 进程**启动期**断言（fail-fast），不通过则拒绝启动 | 服务启动 |
| `REVIEW` | **无法自动化**，只能靠代码审查清单 | 人工，PR 模板逐项勾选 |
| `GATE` | 结构性闸门：服务清单 / 目录结构的人工核对 | 阶段验收 |

**原则**：能被自动化的必须自动化；不能的必须显式标注，不许假装已覆盖。

全文共 **64** 条约束，分类如下（每条只归一类，保守口径：含人工环节即计入人工类）：

| 类别 | 条数 | 执行方式 |
|---|---|---|
| 可自动化（`CI-AST` / `CI-SCHEMA` / `CI-TEST` / `NET` / `RUNTIME`） | **54** | CI 强制，PR 必跑 |
| 必须人工把关（`REVIEW`） | **6** | 见 §5，无自动化手段 |
| 结构性闸门（`GATE`） | **4** | 见 §5，阶段验收时核对 |

部分条款同时有多种手段（如 S-03 兼有 `CI-AST` 与 `CI-TEST`）。**归类采用保守口径**：只要条款的判定中含人工环节（哪怕同时有自动化辅助，如 S-43 的 `CI-AST` + `REVIEW`），即归入人工类，不计入"可自动化"。这样"可自动化"这个数字才是可信的——它表示**完全不需要人**的条款数。64 − 6 − 4 = 54。

## 4. 阶段闸门

每个阶段**进入前**，下列条款必须已全绿。未绿不得开工——这条是硬性的，避免"先写着，回头补检查"。

| 阶段 | 进入前必须已绿 | 对应 §11 验收 |
|---|---|---|
| **1. 内核闭环** | S-05~S-08（分层守卫）、S-09~S-13（Profile 四条不变量）、S-14~S-17（双网关）、S-43~S-44（审批单路径 / 配额入口）、S-49~S-50（部署形态）、S-52~S-56（版本锁与契约冻结）、**S-59（`ignorable` 启动断言）**、**S-60~S-64（品牌与白标）** | 一次提问 → 模型推理 → 工具调用 → 答复，全链路可回放；登录页显示客户公司名与 logo，且改品牌不使会话失效 |
| **2. 企业能力** | S-31~S-34（中文检索与接口冻结）、S-45（审计完整）、S-47（后端唯一执法）、S-01~S-02 已就位 | 两个角色看到的模型 / 知识 / 工具集合不同；中文查询能命中并给原文位置；品牌文案可在后台改，不重新构建镜像 |

## 5. 必须人工把关的条款（共 10 条）

以下 10 条**不假装有自动覆盖**，分两类：`REVIEW`（无自动化手段）靠 PR 模板逐项勾选，`GATE`（结构性闸门）在阶段验收时核对。两类均需架构负责人签字。

### 5.1 `REVIEW` —— 无自动化手段（6 条）

| 编号 | 为什么不能自动化 | 审查问题（PR 模板原文） |
|---|---|---|
| S-26 | "是否真的核验了页面"需读驱动实现逻辑 | 每个动作后是否有独立于 LLM 自述的核验？ |
| S-29 | 读取用户 Cookie 的方式极多，黑名单不可能穷尽 | 是否有任何代码路径触碰用户日常浏览器的 Cookie / profile？ |
| S-36 | "声明式 vs 散写 if"是风格判断 | 脱敏规则是否全部来自字段声明，而非新增的条件分支？ |
| S-43 | 需判断"是否出现了第二条审批实现"（其静态检查只能查已知形式） | 审批是否有唯一入口？是否新增了旁路？ |
| S-51 | 无状态性需人工确认（有无本地落盘、内存缓存） | 宿主是否仍无状态？是否新增了本地持久化？ |
| S-58 | 流程纪律，非代码属性 | 本次升级若失败，产品开发是否仍能推进？ |

### 5.2 `GATE` —— 结构性闸门（4 条）

| 编号 | 核对对象 | 判定 |
|---|---|---|
| S-08 | 后端服务数量与数据库归属 | 是否新增了与主服务共享 MongoDB 的服务？ |
| S-34 | 阶段 2 服务清单 | 是否引入了 ES / 向量库 / 对象存储？ |
| S-49 | 阶段 1 服务清单 | 容器数是否正好 6，且不含额外中间件？ |
| S-57 | 升级流程 | 候选版本是否只在隔离工作区评估，未动线上运行时？ |

> **一处合并说明**：S-08 / S-34 / S-49 三条要求不同，但**复用同一份核对动作**——对照 §4 的服务清单表逐阶段点数。执行时一次核对同时判定三条，不必分三次做。

> **附（规则自动、例外人工）**：S-01 与 S-05~S-07 的**规则**本身是自动检查的，但任何**例外**必须人工批准并登记到 `00` 的"当前临时偏差"。不允许在代码里静默开设例外分支。

## 6. Spec 变更流程

任何对 `00` 的修改，按此顺序执行，缺一步即视为流程违规：

1. **改 `00`**，升版本号（结构变更升次版本 / 澄清升修订号）
2. **更新本文** §3 登记表：新增条款按当前最大编号顺延（当前最大为 `S-64`），作废条款标注 ~~删除线~~ + 作废原因，**不得复用已作废编号**
3. **检查受影响的下游文档**（`01`–`04`），冲突则回改
4. **检查阶段闸门**（§4）：若新条款属于某阶段，补进该阶段进入条件
5. **若涉及已开工阶段**：评估在途代码是否需要同步调整，并登记偏差或计划

### 编号纪律

- `S-nn` **一经分配永不复用**，作废后保留编号并标注作废；
- 一条约束只能有**一个编号**，不得出现"参见 S-12（之一）"这类拆分引用；
- 本文的编号是**唯一引用基准**：代码注释、PR 描述、测试用例名中的 `S-nn` 必须指向本文。
